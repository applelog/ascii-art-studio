## Context

방향이 세 번 바뀌었다. 지금 확정된 것:

- 결과물은 **움직이는 ASCII 아트**다. 글자·숫자·기호만으로 그리고, 전부 코드로 구동한다. **출력물은 Python 코드**다 (`python piece.py`로 실행하면 창에서 움직인다).
- 만드는 방법은 **Claude Code 스킬**이다. `/ascii 파도치는 바다`, `/ascii 우주 속의 눈`, `/ascii 초원을 뛰는 말`처럼 무엇이든 말로 요청하거나 이미지를 붙이면, 제가 그 작품 전용 Python 코드를 새로 써서 파일로 만든다. AI 연결, API 키, 서버는 없다.
- 룩은 고정하지 않고 **요청마다 정한다**.
- **웹앱·갤러리 페이지·Figma 설계는 하지 않는다.** 재생·저장은 Python 쪽에서 한다.
- **한 번에 다 만들지 않는다.** 기능 하나를 만들고, 테스트하고, 직접 실행해 확인한 뒤 결과를 보여 주고 다음으로 간다.
- 명령은 모두 `conda activate min` 뒤에 실행한다. 이 환경에는 Python 3.8, numpy 1.24, Pillow 10.4, OpenCV 4.13, pytest 8.3, tkinter, ffmpeg가 있다. pygame은 없다. [v4+] 2026-11-15 pygame-ce 2.5.2 설치 (재생 창용).

## [v4] 작업 흐름: 단계별 승인

사용자가 정한 스킬의 구동 방식이다. 예: `/ascii 밤하늘에 달빛을 받아서 바다 한가운데 떠 있는 낚시배 만들어줘`

```
요청
 └─ 0. 부족한 정보가 있으면 묻는다 (질문 규칙은 아래 스킬 0번)
 └─ ① 정지 그림      : 완성된 ASCII 아트 사진(PNG)을 먼저 보여 준다
        ↺ 마음에 들 때까지 수정 (횟수 제한 없음)
        ✓ 승인 → 이 그림이 "완성 화면"으로 고정된다
 └─ ② 등장 방식      : 빈 화면에서 완성 화면이 어떻게 나타나는지 구성한다
        ↺ 마음에 들 때까지 수정
        ✓ 승인
 └─ ③ 모션          : 다 나타난 뒤 완성 화면이 어떻게 움직이는지 구성한다
        ↺ 마음에 들 때까지 수정
        ✓ 승인
 └─ 최종본 출력      : Python 코드 + MP4 + 대표 PNG
```

### 핵심 원칙: 결과물은 코드, 사진·영상은 코드의 미리보기

- **이 프로젝트는 생성형 이미지·영상을 만드는 게 아니다.** 결과물은 언제나 **실행되는 Python 코드**(`piece.py`)다.
- 대화 중에 보여 주는 PNG·MP4·프레임 띠는 **그 코드를 실제로 실행해서 뽑은 화면**이다. 코드를 직접 돌려 보지 않아도 바로 확인할 수 있게 하려는 것뿐이다.
- 미리보기를 다른 방법(이미지 생성 AI, 손으로 편집, 코드와 다른 별도 스크립트)으로 만들지 않는다. 항상 `python piece.py --stage N`으로 만든다.
- 그래서 **`python piece.py`를 실행하면 대화에서 본 것과 같은 결과가 나와야 한다.**
  - 창에서 등장 → 모션 반복으로 재생된다.
  - 같은 프레임은 미리보기와 같은 그림이다.
- 미리보기마다 그 결과를 만든 명령과 코드 버전을 함께 알려 준다. 예: "`python pieces/fishing-boat/piece.py --stage 1` (s1_v3)"
- **버전은 그림이 아니라 코드로 남긴다.**
  - `versions/s1_v3/piece.py`에 그 시점의 코드 전체를 저장하고, 미리보기 PNG·MP4를 옆에 둔다.
  - 되돌릴 때는 코드를 되돌린다. 되돌린 코드로 다시 실행하면 같은 그림이 나온다.
- 테스트로 이를 확인한다.
  - 저장된 미리보기 PNG가 현재 코드로 다시 렌더한 같은 프레임과 픽셀 단위로 같다.
  - 최종 MP4의 프레임이 코드 재생 프레임과 같다.
- 창 재생과 MP4가 다를 수 있는 부분은 실제 시간에 따른 재생 속도뿐이다. 느린 기기에서는 창이 프레임을 건너뛸 수 있다. 그림 자체는 같은 프레임 번호면 항상 같다.

### 단계별 규칙

| 단계 | 보여 주는 것 | 수정할 때 바뀌는 범위 | 승인되면 |
|---|---|---|---|
| ① 정지 그림 | PNG 1장 (필요하면 확대 부분 1장) | 구도, 형태, 글자 램프, 밀도, 색. 움직임은 아직 만들지 않는다 | `stage1` 잠금. 이 PNG가 기준 그림 |
| ② 등장 방식 | 등장 과정 MP4와 **프레임 띠**(시간순 6~8장을 이어 붙인 PNG). 등장이 끝난 마지막 프레임은 ①과 같아야 한다 | 등장 순서·방향·길이·글자가 바뀌는 효과. ①의 그림은 바꾸지 않는다 | `stage2` 잠금 |
| ③ 모션 | 반복 구간 MP4와 프레임 띠. 모션의 시작·끝 프레임은 ①과 같은 화면이다 | 무엇이 움직이는지, 속도, 세기, 루프 길이. ①·②는 바꾸지 않는다 | `stage3` 잠금 |
| 최종본 | **`piece.py`(본체)**. 함께 주는 것: `python piece.py`로 실행하는 방법, 확인용 `final.mp4`(등장 1번 + 모션 반복 N번, 같은 코드로 렌더), `still.png`, `GLOSSARY.md` | — | 완료 |

- **한 단계에서 승인 전에는 다음 단계로 가지 않는다.** "마음에 든다", "좋아", "다음" 같은 명확한 승인이 있어야 넘어간다. 애매하면 승인인지 묻는다.
- **수정은 지금 단계만 고친다.** 이미 승인된 단계를 바꿔야 하는 요청이면(예: ③에서 "배를 더 크게"), 어느 단계로 돌아가는지 알리고 확인받는다. 돌아가면 그 뒤 단계는 다시 승인받는다.
- **수정마다 버전을 남긴다.** `pieces/<slug>/versions/s1_v1/`(코드 `piece.py` + 미리보기 `preview.png`), `s1_v2/`, `s2_v1/`(코드 + `preview.mp4` + `strip.png` + `strip.json`) 등. [v4+] `strip.json` 에는 띠를 만든 단계와 프레임 번호를 적어, 테스트가 그 버전 코드로 같은 띠를 다시 만들어 픽셀까지 비교한다. "아까 v2가 나았어"라고 하면 그 버전의 **코드**로 되돌린다.
- **수정 요청이 모호하면 짧게 되묻는다.** 예: "더 예쁘게" → 무엇을 바꿀지 2~4개 선택지로 묻는다.
- 단계마다 결과와 함께 **바꿔 볼 만한 것 2~4개를 제안**한다 (예: ②에서 "위에서 아래로 쓸어내리기 / 노이즈에서 서서히 맞춰지기 / 타자 치듯 왼쪽부터").
- ②·③에서 시간에 따른 움직임은 정지 이미지로 판단하기 어렵다. 그래서 MP4와 프레임 띠를 함께 보여 주고, 움직임의 느낌(속도, 부드러움)은 사용자가 영상을 보고 판단해 준다.

### 등장 방식(②) 후보 예시

고정 목록이 아니라 작품에 맞춰 고르는 예시다.

- 타자기: 왼쪽 위부터 한 글자씩
- 스캔: 위→아래 또는 왼→오른쪽으로 쓸어내림
- 해독: 무작위 글자가 섞이다가 제자리 글자로 맞춰짐
- 밝기 순: 어두운 글자부터 밝은 글자 순으로 채워짐
- 모여들기: 글자가 흩어진 곳에서 날아와 자리를 찾음
- 장면 순서: 하늘 → 달 → 바다 → 배처럼 요소별로 차례로
- 페이드: 바탕에서 서서히 밝아짐

### 작품 파일이 단계를 담는 방식

`piece.py` 맨 앞 설정을 단계별로 나눈다. 아래 코드도 세 부분으로 나눈다.

```python
# ===== ① 장면(정지 그림) 설정 =====
COLS, ROWS = ...; PALETTE = ...; MOON_X, MOON_Y = ...; BOAT_SIZE = ...
# ===== ② 등장 설정 =====
INTRO = "decode"        # 등장 방식 이름 (이 작품에서 정한 것)
INTRO_SECONDS = 3.0     # 등장 길이
# ===== ③ 모션 설정 =====
LOOP_SECONDS = 8; WAVE_SPEED = ...; BOB_HEIGHT = ...
# ===== 최종 출력 =====
FINAL_LOOPS = 3         # final.mp4 에서 모션 반복 횟수
# ===== 코드 =====
def scene(state, grid):              # ① 완성 화면
def intro(state, p, grid):           # ② 등장 진행도 p = 0..1, p=1 이면 scene 과 같음
def motion(state, t, phase, grid):   # ③ phase=0 과 1 이면 scene 과 같음
```

- 엔진이 세 부분을 이어 붙인다: `intro`(INTRO_SECONDS) → `motion` 반복.
- 연결부가 튀지 않도록 **세 화면이 같아야 한다:** ① `scene`, ② `intro(p=1)`, ③ `motion(phase=0)`, `motion(phase=1)`. 테스트로 확인한다.
- 명령줄로 단계별 출력을 만든다:
  - `python piece.py --stage 1` → 정지 PNG
  - `--stage 2` → 등장 MP4와 프레임 띠
  - `--stage 3` → 모션 MP4와 프레임 띠
  - `--final` → 최종본
  - 옵션 없이 실행하면 창에서 재생한다 (등장 후 모션 반복).

### [v4+] 디테일은 사진을 참고해서 만든다 (새로 만드는 모든 대상)

말이든, 배든, 눈이든, 건물이든 **새로 만드는 대상은 상상만으로 그리지 않는다.** 실제 모습을 참고해서 형태와 디테일을 만든다. 낚시배는 예시일 뿐이고, 이 규칙은 모든 작품에 적용한다.

**참고 순서**

1. 사용자가 사진이나 레퍼런스를 줬으면 그것을 먼저 쓴다.
2. 없으면 사진을 검색해서 실제 모습을 확인한다.
   - 예: "작은 목선 낚싯배 옆모습", "galloping horse side view", "human eye close-up"
   - 대상이 여러 종류일 수 있으면 질문 단계에서 어떤 종류인지 묻는다. 예: 배라면 조각배, 어선, 돛단배.

**사진에서 뽑을 것** — `brief.md`의 "참고한 모습" 절에 적는다.

- 전체 비율과 실루엣. 예: 배의 길이:높이, 뱃머리가 들린 정도, 조타실 위치
- 그 대상을 알아보게 하는 특징 부위 3~6개. 예: 낚싯배라면 뱃머리 곡선, 조타실 창, 안테나·마스트, 집어등, 낚싯대 거치대, 타이어 방현재
- 빛을 받는 방향에서 밝은 면과 어두운 면
- 이 글자 해상도(COLS×ROWS)에서 실제로 보일 크기인지. 너무 작은 디테일은 빼거나 과장한다.

**지킬 것**

- 사진은 형태를 보는 참고로만 쓴다. 사진을 그대로 글자로 옮기거나 작품 안에 넣지 않는다. 사용자 사진을 글자로 옮기는 것은 사용자가 원할 때만 이미지 입력(F8)으로 한다.

- 참고한 출처(URL 또는 "사용자 사진")와 거기서 가져온 특징을 `brief.md`에 남긴다.
- 사진에서 실제로 본 것과 추정한 것을 나눠 적는다.
- 특징 부위는 맨 앞 설정 변수로 둔다(예: `BOW_RISE`, `CABIN_W`, `ANTENNA_ROWS`). 그래야 "창을 더 크게" 같은 수정이 쉽다.

### [v4+] 작품 안의 임시 함수 → 엔진 함수로 교체

- 엔진에 아직 없는 기능을 작품 안에 임시로 짰다면, 엔진에 같은 기능이 생긴 뒤 엔진 것으로 바꾼다. 예: 낚시배의 `cell_hash`, `value_noise`, `lum_to_chars`, `palette_color`.
- 바꾼 뒤 그 작품의 승인된(또는 검토 중인) 버전 미리보기와 **픽셀까지 같은지** 확인한다.
  - 같으면 코드 정리 버전으로 저장한다.
  - 다르면 차이를 보여 주고, 그림이 바뀌는 것을 사용자에게 확인받는다.
- 보류된 작품은 보류가 풀릴 때 바꾼다.

### [v4+] 3D 요청 (2026-11-15 추가)

ASCII에서 3D란 3D 공간의 물체·카메라·빛을 계산해 그 결과를 글자 칸에 그리는 것이다 ("돌아가는 ASCII 도넛" 방식). 화면은 그대로 2D 글자다.

- **질문 단계에서 어떤 3D인지 먼저 묻는다.** 결과가 크게 갈리는 항목이다.
  - 움직임: 물체가 제자리에서 돎 / 카메라가 물체 주위를 돎 / 장면 속으로 날아 들어감
  - 표현: 면을 밝기로 채움 / 선(와이어프레임) / 점(포인트 클라우드)
  - 빛과 재질: 빛 방향, 그림자 유무, 매끈함·각진 면
  - 회전 축과 속도
- **그리는 방법 고르기**
  - 매끈한 물체·합쳐진 형태·그림자 → SDF 레이마칭
  - 각진 물체·주어진 모델 → OBJ 모델 (면 칠하기 또는 선)
  - 입자·별·돈 비 같은 것 → 3D 점
- 참고 사진 규칙은 그대로다 (대상의 실제 형태 확인). 회전 속도, 카메라 거리, 빛 방향, 도형 크기는 맨 앞 설정 변수로 둔다.
- **루프:** 회전은 phase 의 정수 바퀴로 한다. 그러면 phase 0 과 1 의 장면이 같다.
- **한계**
  - 사진 한 장으로 진짜 3D 모델을 만들 수는 없다. 밝기를 깊이로 쓰는 흉내만 가능하다.
  - 물체가 많거나 그림자가 들어간 복잡한 장면은 numpy 계산이 무거워진다. 해상도를 낮추거나, setup 에서 미리 계산하거나, 창 재생의 미리 계산·캐시에 기댄다.
  - Blender 같은 외부 3D 프로그램은 쓰지 않는다.
- **측정 (2026-11-15):** 회전 도넛 레이마칭, 120×60칸 기준 칸당 1점이면 18ms/프레임, 칸당 2×2점이면 65ms/프레임.
- **F8.5 결과 (2026-11-15):** 3D 데모(바닥·그림자·점 고리, 프레임당 약 40~60ms)를 한 프로세스로 계산하면 창 첫 바퀴가 초당 10프레임이었다. 작업자 프로세스 6개(asciiart/worker.py, multiprocessing 없이 파이프로 통신)로 미리 계산하게 해서 첫 바퀴부터 초당 30프레임이 됐다. 최종본 435프레임 저장은 10초. 첫 프레임 계산이 12ms 를 넘는 작품에만 작업자를 쓴다.

### 2) eyeTutorial에서 가져올 개발 방식

이 작품은 "그림을 픽셀 단위로 계산한 뒤 글자로 바꾸는" 방식이다. "글자를 직접 배치하는" 방식과 다르다. 엔진은 두 방식을 모두 지원한다.

| 기법 | eyeTutorial에서 본 것 | 이 프로젝트에 넣는 곳 |
|---|---|---|
| 필드 렌더 | 눈·성운·우주를 numpy 픽셀 배열로 계산. 이미지 파일 없음 (Procedural) | `asciiart/shade.py`: 셀마다 `(x, y, t) → RGB`를 numpy로 한 번에 계산 |
| 슈퍼샘플링 | 셀 하나를 2×2로 계산해 평균 (`SS = 2`) | 설정 `SUPERSAMPLE` (1~3) |
| 밝기 → 글자 | `lum = 0.30R + 0.60G + 0.10B`, 감마 `lum ** 0.72`, 셀마다 고정 디더(`HSC`)를 더해 램프 단계 선택 | `ramp.py`: `GAMMA`, `DITHER` 변수, 긴 램프 프리셋 |
| 셀 단위 색 | 셀마다 RGB를 24단계로 양자화(`QL`)하고 색 캐시 | grid에 셀별 RGB, 설정 `COLOR_LEVELS` |
| 블룸·톤매핑·비네트 | 밝은 영역을 흐려 더하고, `1 - exp(-2x)`로 압축하고, 가장자리를 어둡게 | `post.py`: 글자로 바꾸기 **전에** 색 필드에서 처리 (`BLOOM`, `EXPOSURE`, `VIGNETTE`) |
| 장면 타임라인 | 시간 상수로 막을 나눔: `T_OPEN`, `T_OPEN_D`, `T_BLINK`, `T_Z0`, `T_ZD`, `ZEND`, `T_SPACE`, `T_HEART`, `T_HEART_D`. 눈이 열리고(오버슈트), 깜박이고, 지수 줌으로 동공 안의 우주로 넘어감 | `ease.py`: `smoothstep`, `ease`, `overshoot`, `segment(t, 시작, 끝)`, 키프레임. **막의 시작·길이도 맨 앞 설정 변수로 둔다** (`T_<막>`, `T_<막>_D`) |
| 값 노이즈 | 여러 옥타브 값 노이즈(`tex2d`, `noise1d`)를 bilinear(`bil`)로 샘플. 홍채 결, 핏줄, 성운에 사용 | `noise.py`: seed 기반, 루프용 원형 시간 노이즈 포함 |
| 무작위 사건 | 별똥별·혜성이 무작위 간격으로 등장 | `setup`에서 seed로 **일정표를 미리 만든다** → 다시 재생해도, 탐색해도, 저장해도 같은 결과 |
| 변경 셀만 다시 그리기 | 글자나 색이 바뀐 셀만 갱신하고, 그리기 예산(`TK_MS`)을 측정해 조절 | `player.py`: 화면 갱신 비용을 측정해 표시. 저장은 항상 전체 프레임 |
| 키 조작 | R 다시 시작, Esc 종료 | Space 정지, R 처음부터, S 저장, ←→ 프레임 이동, Esc 종료 |
| 용어집 | 모든 상수·함수·변수를 `Glossary.txt`에 설명 (아래 3절) | 작품마다 `GLOSSARY.md` |

### 3) eyeTutorial `Glossary.txt` 방식 → 작품마다 용어집

eyeTutorial의 용어집은 `--- 절 이름 ---`으로 나뉘고, 각 줄이 `이름 : 뜻` 형식이다. 절 순서는 다음과 같다.

1. 일반 용어
2. 맨 앞 설정 상수
3. 함수
4. 난수·텍스처 변수
5. 장면 요소별 변수 (별, 눈 움직임 등)
6. 크기·좌표
7. 장면 함수별 지역 변수
8. 렌더 변수
9. 메인 루프
10. 키

이 프로젝트에서는 작품마다 `pieces/<slug>/GLOSSARY.md`를 같은 구조로 쓴다. 두 가지를 보완한다.

- **범위·단위 칸을 추가한다.** 원본은 단위가 뜻 안에 가끔만 있다. 형식은 `이름 : 뜻 : 단위·범위`로 한다. 예: `T_OPEN : 눈이 열리기 시작하는 시각 : 초, 0~LOOP_SECONDS`.
- **이름 하나에 뜻 하나만 쓴다.** 원본은 `hx`가 세 가지, `q`와 `cl`이 두 가지 뜻으로 쓰였다. 스킬 규칙으로 금지하고, 테스트가 용어집에 같은 이름이 두 번 나오는지 검사한다.

# --- 시간 ---

# --- 막(장면) 타이밍 (eyeTutorial 방식) ---
T_ENTER, T_ENTER_D = 0.0, 0.8          # 등장 시작, 길이(초)

# --- 효과 ---

**코드 맨 앞에 조절 변수를 모은다 (C의 `#define`처럼).**

- 그 값만 바꾸면 아래 코드 전체가 따라 바뀐다. 아래 코드에는 숫자를 직접 쓰지 않고 모두 위 변수에서 가져온다. 0, 1, π 같은 수학 상수는 예외다.

- 엔진(`config.py`)이 범위를 검사한다. 잘못된 값은 보정하고 경고를 출력한다. 작품 고유 변수의 범위는 `RANGES = {"SPEED": (0.25, 4)}`로 둔다.
- 명령줄에서 값을 덮어쓸 수 있다: `python piece.py --set SPEED=2 --set COLS=200`. 파일을 고치지 않고 시험할 때 쓴다.

**규칙:**

- `frame`은 그리는 일은 하지 않고 `grid`만 채운다. 덕분에 창 없이 테스트할 수 있다.
- 작품마다 엔진 위에 자기만의 형태·모션 코드를 자유롭게 쓴다. 정해진 스타일 목록은 없다.
- 렌더 경로에서 `random`, `time`, `np.random`(seed 없는 것)은 쓰지 않는다. 같은 프레임 번호면 항상 같은 그림이 나와야 탐색과 저장이 맞는다.
- 잔상처럼 이전 프레임에 기대는 효과는 엔진이 처리한다. 탐색할 때는 엔진이 필요한 만큼 앞 프레임부터 다시 그려 같은 결과를 낸다.

## /ascii 스킬이 하는 일

0. **애매하면 먼저 묻는다.** 요청이 짧아서 결과가 크게 갈리는 항목이 비어 있으면, 코드를 쓰기 전에 선택지를 주고 물어본다.

   **질문 항목은 고정된 목록이 아니다.** 요청한 대상과 장면을 보고, 그 작품의 결과에 가장 큰 영향을 주는 항목을 그때그때 고른다. 아래는 대상 유형별 **예시일 뿐**이고, 어떤 유형의 질문을 다른 작품에 그대로 적용하지 않는다.

   | 요청 예 | 대상 유형 | 이런 것을 물을 수 있다 |
   |---|---|---|
   | `/ascii 초원을 뛰는 말` | 이동하는 생물 | 제자리인지 가로지르는지(어디서 어디로), 방향과 시점, 걸음걸이와 속도, 배경을 같이 그릴지 |
   | `/ascii 파도치는 바다` | 자연 현상·풍경 | 바다를 보는 시점(수평선 정면·위에서·해변), 파도 세기와 리듬, 시간대와 빛(낮·노을·밤), 거품·물보라 표현 |
   | `/ascii 우주 속의 눈` | 장면 전환·초현실 | 막 구성(눈 → 줌 → 우주처럼 이어지는지, 둘이 겹쳐 있는지), 전체 길이와 막별 시간, 분위기(차분·긴장), 반복할지 한 번 재생할지 |
   | `/ascii LOVE` | 글자·타이포 | 글자가 어떻게 등장·변형되는지, 읽을 수 있는 상태를 얼마나 유지할지, 글자 크기와 배치 |
   | `/ascii 회전하는 3D 도넛` | 3D 물체·장면 | 물체가 도는지 카메라가 도는지, 면·선·점 중 표현 방식, 빛과 그림자, 재질, 회전 축과 속도 |
   | 사진 첨부 | 이미지 기반 | 무엇을 움직일지(사진 자체·주변 효과), 원본 색을 쓸지 다시 칠할지, 피사체만 쓸지 배경도 쓸지 |

   어느 작품에나 해당할 수 있는 공통 후보: 그리는 방식(밝기 글자 채움 / 윤곽선 기호 / 둘 다)과 글자 밀도, 색과 바탕 밝기, 루프 길이, 반복 여부. 이것도 요청에 이미 드러났거나 결과에 큰 차이가 없으면 묻지 않는다.

   규칙:
   - 한 번에 최대 4개만, 결과에 가장 큰 차이를 내는 것부터 묻는다.
   - 질문마다 추천안을 첫 번째 선택지로 둔다.
   - 각 선택지 설명에 그 선택으로 화면이 어떻게 보이는지 한 줄로 적는다.
   - 요청에 이미 적힌 것은 다시 묻지 않는다.
   - 사용자가 "알아서"라고 하면 묻지 않고, 정한 기본값을 `brief.md`에 적는다.
   - 이미지만 왔고 움직임 설명이 없으면 움직임은 반드시 묻는다. 정지 이미지로 움직임을 정하지 않는다.
   - 수정 요청(`/ascii horse-meadow 더 느리게`)처럼 대상이 분명하면 묻지 않는다.
1. **요청 해석.** 주제, 장면, 움직임, 리듬, 색, 분위기를 `brief.md`에 적는다. 관찰한 것(이미지에 실제로 있는 것), 추정한 것, 사용자가 지정한 것, 미확인인 것을 나눠 쓴다.

   `brief.md` 구성:
   ```md
   # <제목>
   ## 요청            (사용자 원문 그대로)
   ## 답변으로 정한 것  (질문과 답)
   ## 기본값으로 정한 것
   ## 이미지에서 관찰한 것 / 추정한 것 / 확인 못 한 것   (이미지가 있을 때만, 섞지 않는다)
   ## 참고한 모습 [v4+]   (출처 URL 또는 "사용자 사진", 가져온 비율·특징 부위·빛, 본 것과 추정한 것 구분)
   ## 설계
   - 그리는 방식: 필드 렌더 | 글자 배치 | 혼합 — 이유
   - 막(act) 구성: 0~2s ..., 2~4s ...
   - 루프: phase 0과 1이 어떻게 이어지는지
   ```
2. **이미지가 있으면** `tools/image_to_field.py`로 필드를 뽑는다. `--cols`와 `--cell-aspect`는 작품 설정과 같은 값을 쓴다. 원본 이미지는 `pieces/`에 복사하지 않는다. 피사체가 제대로 분리됐는지(png 투명도 / 가장자리 배경색 차이) `brief.md`에 적는다.
2-1. **[v4+] 참고 사진으로 디테일 정하기.** 사용자 사진이 있으면 그것을, 없으면 사진 검색으로 실제 모습을 확인한다. 비율, 실루엣, 특징 부위 3~6개, 빛을 `brief.md`의 "참고한 모습"에 적고, 특징 부위를 맨 앞 설정 변수로 만든다 (위 "디테일은 사진을 참고해서 만든다" 규칙).
3. **`pieces/<slug>/piece.py` 작성.**
   - 먼저 그리는 방식을 고른다. 빛·질감·연속된 장면이면 필드 렌더(eyeTutorial식), 선명한 기호·윤곽·입자면 글자 직접 배치다. 둘을 섞을 때는 필드를 먼저 grid로 바꾸고 그 위에 글자를 놓는다.
   - 장면 전환이 있으면 막(act)으로 나눠 `ease.py`로 연출하고, 막 타이밍을 맨 앞 설정 변수로 둔다.
   - 형태는 SDF, 파라메트릭 곡선, 3D 점 투영, 이미지 필드 중에서 고른다.
   - 움직임은 주기 함수로 짜서 루프가 이어지게 한다. 루프 작품은 모든 시간 변화를 phase의 **정수 주기**로 만든다.
   - 글자 선택은 밝기 풀에 반짝임을 더하고, 윤곽선에는 방향 글자를 쓴다.
   - 무작위 사건은 setup에서 seed로 일정표를 만든다.
   - 후처리는 필요할 때만 잔상과 글로우를 넣는다.
4. **`GLOSSARY.md` 작성** (eyeTutorial 형식에 범위·단위 칸 추가, 이름 하나에 뜻 하나).
4-1. **[v4] 단계별로 진행한다.** 위 3번(코드 작성)은 한 번에 끝내지 않는다. "작업 흐름: 단계별 승인"에 따라 ① 정지 그림(`scene`)만 먼저 만들어 PNG를 보여 주고, 승인 후 ② `intro`, 그다음 ③ `motion`을 만든다. 각 단계는 승인될 때까지 수정을 반복하고, 승인된 단계의 코드와 설정은 사용자가 요청하지 않는 한 건드리지 않는다.
5. **검증.**
   - `pytest`로 결정성, phase 0과 1의 일치, 설정 변경 반영, 프레임 예산, 금지 함수, 용어집 중복을 확인한다.
   - [v4] 단계 연결 확인: `scene` = `intro(p=1)` = `motion(phase=0)` = `motion(phase=1)`.
   - 직접 실행해 시작·중간·끝 근처 프레임을 PNG로 저장해 본다. 형태가 읽히는지, 움직임이 요청과 맞는지, 루프 이음매가 튀지 않는지 판단한다.
   - 직접 보지 않은 것은 "확인함"이라고 하지 않는다.
6. **보고.** 무엇을 만들었는지, 파일 링크, 스크린샷 또는 MP4를 보여 준다. 바꿔 볼 만한 설정 변수 3~5개를 "이 값을 바꾸면 이렇게 된다" 형식으로 적고, 테스트 결과와 확인하지 못한 것을 적는다.
7. **수정 요청** (`/ascii ocean-waves 파도를 더 높게`, `/ascii horse-meadow 더 느리게`)은 해당 작품 파일에서 관련 부분만 고친다. 값 조정으로 되면 맨 앞 설정만 고친다.

## 이미 만든 것의 처리

- 지난 턴에 쓴 TypeScript 런타임(`src/runtime/*`)과 테스트(`tests/*.ts`)는 F1에서 백업 후 지운다. 설계는 Python으로 옮긴다: grid 분리, 결정성, 설정 범위 검사, 잔상 탐색 재구성, 램프·디더, 필드 렌더, 블룸·톤매핑.
- `tools/image_to_field.py`는 이미 Python이고 테스트도 했으니 그대로 쓴다.
- `.claude/skills/ascii/SKILL.md`의 질문 규칙은 유지하고, 경로·명령·템플릿만 F9에서 Python으로 바꾼다. 그 전까지 이 스킬을 쓰지 않는다. `template.ts`는 F9에서 `template.py`로 바꾼다.
- Figma 파일([Web Structure](https://www.figma.com/design/QGlgmN2ELZ8EdM6f9IERNJ))은 더 쓰지 않는다. 지울지는 사용자가 정한다.
- 메모리의 "웹 화면은 Figma 먼저" 규칙은 이 프로젝트에서 빼도록 고친다.

## 검증

- `pytest`:
  - 같은 seed와 같은 프레임이면 grid와 프레임 이미지가 같다.
  - 맨 앞 설정 값(예: `SPEED`, `COLS`)을 바꾸면 결과가 실제로 바뀐다.
  - 루프 작품은 phase 0과 1의 grid가 일치한다.
  - 렌더 경로에서 `random`과 `time`을 쓰지 않는다.
  - 한 프레임 계산이 예산 안에 든다.
  - 용어집에 같은 이름이 두 번 나오지 않는다.
  - MP4의 프레임 수, 길이, 해상도가 맞다.
  - [v4] 단계 연결: `scene` = `intro(p=1)` = `motion(phase=0)` = `motion(phase=1)` (글자와 색이 같다).
  - [v4] 최종 MP4 길이 = `INTRO_SECONDS + LOOP_SECONDS × FINAL_LOOPS`.
  - [v4] 미리보기 = 코드: 저장된 단계별 PNG와 최종 MP4의 프레임이 지금 코드로 다시 렌더한 결과와 같다. 버전 폴더의 코드를 실행하면 그 버전의 미리보기와 같은 그림이 나온다.
- 직접 실행: 창 재생, 탐색 재현, PNG 크기, MP4 저장을 확인한다. 측정한 성능은 기기와 함께 기록한다.
